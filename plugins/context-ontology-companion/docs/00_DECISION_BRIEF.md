# 00. 대화 요약과 결정 기준

기준일: 2026-09-05 / 문서 상태: 의사결정 기록 + 검토 가능한 설계 제안.

## 대화가 도달한 결론

처음 목표는 Codex가 긴 작업과 세션 변경 중에도 중요한 문맥을 잃지 않도록 하는 것이었습니다. 이를 모델의 컨텍스트 창 확대가 아니라 외부의 지속 가능한 지식 저장과 필요한 문맥의 재구성 문제로 보았습니다.

Code Ontology Companion의 코드 그래프에 대화·결정·목표·제약·출처·시점을 연결하면, “어떤 코드가 있는가”뿐 아니라 “왜 이렇게 만들었는가”를 설명할 수 있다는 방향이 나왔습니다. 그러나 코드 정적 분석과 사용자 문맥 보관은 사용자 가치, 데이터 민감도, 쓰기 권한, 운영 방식이 다릅니다.

소유자는 **별도 Plugin + 공통 계약·코어**를 최우선 방향으로 채택했고, 새 설계·개발 저장소에서 Codex가 설계를 보완·검토한 뒤 개발과 공개 플러그인 등록을 수행하도록 요청했습니다.

## 소유자가 승인한 사항

| ID | 승인된 방향 |
| --- | --- |
| D-01 | Code Ontology Companion의 정체성을 유지하고 Context 제품을 별도 플러그인으로 만든다. |
| D-02 | 두 제품은 공통 데이터 계약과 적절한 공통 코어를 재사용한다. |
| D-03 | 최종 배포 목표는 공개 ChatGPT 플러그인이다. |
| D-04 | 정해진 출시 순서에 따라 Codex가 검토·보완·개발·등록 준비를 진행한다. |
| D-05 | 새 설계·개발 저장소에 대화 요약, 설계, 인계 문서를 둔다. |
| D-06 | 새 제품 이름은 `context-ontology-companion`이다. |
| D-07 | `ontology-companion-contracts`도 별도 공개 플러그인으로 만든다. |

두 제품명과 Contracts 별도 공개 플러그인 목표는 사용자 명시 요구입니다. 이전 패키지가 이를 단순 기본값/라이브러리로 처리한 누락을 수정합니다.

초기 비공개, 언어·DB·호스팅, 구체적인 도구 수, 수치 목표, 라이선스는 여전히 **제안 기본값**입니다. “Contracts → Code → Context” 표기는 이번 재평가에서 공통 계약을 두 형제 제품이 소비하는 구조로 구체화합니다. 이는 설치·권한·런타임 호출의 자동 상속을 뜻하지 않습니다.

## 앞선 설명에서 보정할 점

| 이전 아이디어 | 이 설계의 정확한 해석 |
| --- | --- |
| 사실상 제약 없는 컨텍스트 | 저장량을 늘릴 수 있지만 검색 누락·토큰·비용·보존 한도는 존재한다. 무제한·무손실을 보장하지 않는다. |
| 원본 대화를 반드시 영구 보존 | 전체 채팅을 수집하지 않는다. 승인한 최소 문장·선택된 근거만 필요 범위에서 보관한다. |
| 직접 진술은 높은 신뢰도의 사실 | 사용자가 그렇게 말했다는 출처 증거이지, 외부 세계의 사실임을 자동 입증하지 않는다. |
| 새 문장이 항상 이전 문장을 대체 | 주체·프로젝트·조건·유효시간과 사용자의 대체 의도를 확인한다. 충돌은 표시하고 자동 확정하지 않는다. |
| 불변 이력을 영원히 보관 | 감사 메타데이터와 지식 본문을 분리한다. 삭제 요청은 본문·파생 데이터까지 처리해야 한다. |
| Skills만 설치하면 세션 간 자동 기억 | 스킬은 절차다. 지속 저장소와 허용된 호출 경로가 별도로 필요하다. |
| 메모리를 읽으면 새 행동도 승인 | 과거 기록은 현재 실행 권한이나 사용자 동의가 아니다. |
| 분리하면 심사에 가장 유리 | 책임·데이터 경계를 명확히 하는 설계 판단이다. 심사 통과나 기간을 보장하지 않는다. |
| 날짜가 2026-08-26인 이전 답변 | 이 패키지는 실제 검증 기준일 2026-08-29를 사용한다. 이전 답변의 시각을 사실 출처로 재사용하지 않는다. |
