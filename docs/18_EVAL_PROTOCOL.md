# 18. 평가 프로토콜 — 검색보다 작업 재개를 검증

상태: 실행 전 제품 평가 계획. 기존 37개 시나리오와 별도로 v2 추가 사례를 관리합니다.

## 왜 새 평가가 필요한가

스키마 통과, 문서 링크 정상, 단위 시험 개수는 필수이지만 사용자 가치의 증거가 아닙니다. 목표는 세션을 바꾼 뒤 에이전트가 원래 요구와 제약을 유지하며 다음 작업을 올바르게 수행하는 것입니다. OpenAI 평가 지침도 실제 작업별 성공 기준과 반복 비교를 강조합니다. 출처는 `13_SOURCES_AND_VERIFICATION.md`를 봅니다.

## 비교군

| ID | 방식 | 목적 |
| --- | --- | --- |
| B0 | 같은 승인 자료를 예산 내 직접 제공 | 자료가 짧으면 그래프가 불필요할 수 있음을 확인 |
| B1 | 직전 최신 요약 + 필요한 원문 조회 | 일반적인 체크포인트 방식과 비교 |
| B2 | 승인 Markdown/JSON + 구조화/키워드 검색 | 단순 외부 기억 기준선 |
| C1 | 같은 자료 + 명시적 관계 + 문맥 재구성기 | 관계/시간/충돌 처리의 추가 가치 |

B0에 자료가 다 들어가지 않는 사례는 '예산 내 직접 제공 불가'로 분리하고 임의로 실패 점수 0을 부여하지 않습니다. 정보량이 다른 비교를 모델/아키텍처 우월성으로 해석하지 않습니다.

## 통제 변수

동일한 합성 또는 별도 승인·비식별 자료, split, 시점, 데이터 리비전, 사용자 권한, 질문, 출력 예산을 사용합니다. 모델·버전·reasoning 설정·도구·동시성·재시도·측정 tokenizer를 기록합니다. 같은 사례를 여러 seed 또는 반복 회차로 측정하고 성공/총수와 불확실성을 공개합니다.

Astra/Sol 비교는 **실제 두 모델에 접근할 수 있을 때** 별도 실험 축으로 시행합니다. 한 모델의 출력 품질을 보고 다른 모델의 점수를 추정하지 않습니다. 같은 모델 비교로 파이프라인 효과를 먼저 확인한 뒤 모델 차이를 분리합니다.

## 1차 평가 자료

제안: 독립 사례 120개, 튜닝 40개와 보류 평가 80개. 언어는 한글 중심으로 하고 영어/혼합 식별자 사례를 포함합니다. 프로젝트·주제 단위로 분리해 같은 결정의 표현만 바꾼 자료가 양쪽에 새지 않게 합니다. 규모는 개발 예산에 맞게 바꾸되 변경 이유를 기록합니다. 숫자는 기존 성능 또는 통계적 유의성을 보장하지 않습니다.

각 사례에는 질문, 사용자 권한, 적용 시점, 필요한 근거 ID, 반드시 유지할 제약, 금지된 결과, 허용되는 불확실성 답변, 다음 작업의 성공 판정기를 둡니다. 코드 작업은 sandbox의 실제 assertion으로 검증하고, 의미 판정은 검토자가 확인합니다. 모델 단독 채점은 보조 신호입니다.

## 주 지표

| 지표 | 판정 방법 |
| --- | --- |
| 작업 재개 성공률 | 필요한 다음 행동을 수행하면서 모든 필수 제약을 유지한 사례/전체 실행 가능 사례 |
| 필수 제약 보존율 | 포함되어야 하는 적용 제약 중 정확한 근거와 함께 보존된 비율 |
| 잘못된 확정률 | 충돌/정보 부족/미승인 사안을 확정으로 처리한 비율 |
| 근거 충실도 | 응답의 주장이 실제 참조 근거와 일치하는지 검토 |
| 과거 정보 오용률 | 다른 프로젝트/환경/유효 시점의 정보를 현재 사실로 사용한 비율 |
| 자원 비용 | 성공 작업당 측정 토큰·지연·호출 수·금액 또는 측정 불가 |

Recall@K는 보조 지표로 유지합니다. 정답 문서가 검색돼도 제약을 무시하면 작업 실패입니다. 검색 못한 경우, 필요한 자료가 없는 경우, 권한이 없는 경우를 별도로 집계합니다.

## 출시 판정

보안·삭제·승인·범위 시험에서 알려진 중대한 실패가 없어야 합니다. 시험에서 누출 0건은 미지의 모든 입력에 대해 안전하다는 증명이 아닙니다. 단순 기준선보다 복잡한 C1을 선택하는 이유는 사전에 정한 작업 품질/비용 비교로 입증합니다. 이득이 없으면 공통 계약과 단순 저장·검색을 남기고 과도한 그래프 확장을 보류합니다.

공개 등록용 5개 긍정/3개 부정 예제는 심사자가 사용 흐름을 확인하는 자료이지 전체 품질 시험의 대체물이 아닙니다.

## 실행 상태 분리

- `package_test`: 문서·스키마·manifest·bootstrap 모의 시험.
- `reference_experiment`: 합성 후보 그룹의 예산/원자성 참조 로직.
- `product_unit` / `product_integration`: 실제 core/DB/승인 구현.
- `host_e2e`: 실제 ChatGPT/Codex 환경의 저장/복구/정정/삭제.
- `task_benchmark`: 위 통제 조건의 사용자 작업 재개 평가.

이번 번들에서 실행한 것은 첫 두 종류뿐입니다. 나머지는 `not_run`입니다.
