# 12. 미결정 사항과 위험

## 소유자 결정이 필요한 항목

| 항목 | 제안 기본값 | 결정 시점 / 영향 |
| --- | --- | --- |
| 새 저장소 이름 | context-ontology-companion | 원격 생성 시 이름 충돌 확인 |
| 초기 visibility | private | public 전환은 별도 승인 |
| 라이선스 | Apache-2.0 | 공개 코드/계약 배포 전 확정 |
| 월 운영 예산 | 아직 없음 | 유료 인프라 생성 전 필수 |
| 운영 주체/도메인 | 아직 없음 | OAuth·privacy·지원·심사 전 필수 |
| 데이터 보관 지역 | 아직 없음 | 실제 호스팅/정책 결정 전 필수 |
| 보존·백업 기간 | 짧은 draft TTL, 관리 백업 최대 30일 제안 | 운영 시험 후 정책에 반영 |
| 공개 국가/언어 | 유지 가능한 최소 범위 | 공개 listing 준비 시 결정 |
| 지원/사고 대응 | 단일 지원 채널과 중단 절차 제안 | 실제 사용자 수용 전 필수 |

이 결정이 없더라도 synthetic fixture를 이용한 설계·로컬 개발은 진행할 수 있습니다. 소유자에게 같은 질문을 반복하지 말고 승인되지 않은 외부 작업만 멈춥니다.

## P0에서 기술적으로 검토할 항목

| 위험 | 확인할 질문 | 대안 |
| --- | --- | --- |
| 별도 승인 웹 화면의 마찰 | 호스트가 검증 가능한 transaction-bound 승인을 제공하는가? | 자체 승인 화면 유지/적합한 host primitive |
| 한국어 검색 품질 | 전문/부분문자열+alias가 패러프레이즈를 충분히 찾는가? | 측정 후 로컬/선택적 embedding |
| 공통화 비용 | 두 제품에서 실제로 같은 코드가 쓰이는가? | 계약만 공유, runtime 추출 지연 |
| 출처 복원 불가 | 호스트가 원문 ID를 제공하는가? | 짧은 승인 excerpt 또는 source unavailable |
| 모델 후보 오추출 | 사용자가 원문과 정규화 결과를 쉽게 비교하는가? | 작은 payload와 변경 강조 |
| 삭제 복잡성 | 모든 파생물의 lineage가 추적되는가? | MVP 파생 저장소 수 최소화 |
| 데이터베이스 차이 | 개발 adapter와 운영 transaction이 같은가? | 운영 DB E2E를 gate로 유지 |
| 공개 경로 변경 | 현재 계정·표면·포털에서 supported 형태인가? | 공식 문서 재확인, 실제 호스트 spike |

## 판단을 왜곡하지 않을 원칙

좋아 보이는 이름이나 “무제한 기억” 문구로 제품 가치를 평가하지 않습니다. 기본 메모리와 무엇이 다른지, 결정의 근거를 실제로 다시 찾는 데 도움이 되는지 검증합니다.

공개 심사 통과·리뷰 기간·사용자 증가·월 비용을 근거 없이 예측하지 않습니다. 분리 구조의 장점은 책임·권한·데이터 경계가 명확하다는 설계 판단이지 성공 보증이 아닙니다.

## v2 상태 정정

두 제품명과 Contracts 별도 공개 플러그인 목표는 더 이상 미정이 아닙니다. 초기 저장소 가시성, 호스팅, 비용, 최종 공통 schema/profile, 실제 호스트 실행 가능성, 공개 등록 일정은 확인이 필요합니다. 플랫폼의 자동 plugin-to-plugin 의존성/권한 상속은 전제로 두지 않습니다. 과거 404를 새 저장소 생성의 충분한 증거로 사용하지 않습니다.
