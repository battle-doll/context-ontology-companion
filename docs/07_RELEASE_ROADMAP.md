# 07. 출시 로드맵 — 공통 계약과 공개 플러그인의 순서 분리

2026-09-05 수정. 이름과 공개 목표는 확정되어 있으며, 저장소가 존재하는지·현재 권한으로 보이는지는 별도 확인합니다.

## P0 — 기준선과 위험한 가정 확인

기존 Code 저장소의 실제 리비전을 읽기 전용으로 기록합니다. 두 새 저장소/작업 폴더의 상태와 플랫폼 기능을 확인합니다. 기존 설계 검토를 반복하되 새로운 발견과 이미 해결된 항목을 구분합니다. 원본에도 있던 인증·승인 UX 호스트 시험을 초기 spike로 유지합니다.

산출물: 짧은 검토 보고서, 역할/도구 관측 정보, 사용자 요구 추적표, 호스트별 지원/미지원 표. 장기 과제는 단순 목표 하나에서 시작합니다.

## P1a — 최소 계약 초안 + 실제 소비자 한 경로

공통 metadata/evidence 부분과 Context profile을 정의하되 정식 안정성을 먼저 선언하지 않습니다. 합성 결정 한 개를 승인 초안으로 만들고, 승인 모의 경로와 저장/조회/근거 표시를 연결합니다. 모의 승인을 실제 사용자 인증 완료로 기록하지 않습니다.

동시에 Contracts 제품에서 이 소비자의 교환 자료를 검증하는 최소 workflow를 만듭니다. Code legacy 자료의 mapping fixture를 만들되 Code 저장소는 변경하지 않습니다.

완료 조건: 두 프로필이 서로의 필수 필드를 잘못 요구하지 않음, 지원하지 않는 버전/프로필 거절, 실제 소비자가 사용한 초안과 검증기가 일치.

## P1b — 첫 계약 릴리스와 호환성 기준

P1a 결과로 필요한 필드만 확정합니다. 스키마·프로필·검증기 버전과 artifact digest를 구분하고 pin합니다. 기존 Context draft-0.1은 과거 계약으로 보존하고 새 profile과 자동 동등하다고 간주하지 않습니다.

**계약 패키지 릴리스**가 이후 개발의 기술 기반입니다. **Contracts 플러그인 디렉터리 승인**은 이 단계의 필수 기술 의존성이 아닙니다.

## P2 — Context MVP와 Contracts 플러그인 병행 완성

Context: 저장·검색·현재 문맥 재구성·정정·철회·삭제·내보내기와 최소 승인 화면을 구현합니다. 필수 제약/충돌/근거의 원자성, 동시성, 격리, 삭제 시험을 추가합니다. 기본 경로는 별도 서버 LLM API 없이 작동하도록 유지합니다.

Contracts: 지원하는 교환물 검증, 프로필/버전 비교, 손실을 명시한 migration plan을 제공하는 독립 공개 plugin을 구현합니다. 초기에는 executor가 확인된 skill+script 형태를 우선하고, 원격 MCP는 실제 지원 표면/수요에 따라 별도로 결정합니다.

완료 조건: 각 제품이 다른 제품의 설치 없이 사용자 workflow를 수행. Contracts로 schema-valid였다는 이유로 사실/권한까지 검증됐다고 주장하지 않음.

## P3 — 제품별 공개 등록

각 제품은 `local-tested → host-tested → submission-ready → submitted → approved → published`를 따로 관리합니다. 실제 디렉터리/호스트 정책에 맞는 패키지를 검증합니다. 구현되지 않은 도구의 제출 manifest는 만들지 않습니다.

권장 공개 순서는 준비된 Contracts 플러그인, Context 플러그인 순서입니다. 그러나 첫 제품의 심사 지연 때문에 두 번째의 로컬 개발을 멈추지 않습니다. 비용/개인정보/호스팅/공개 전환/최종 법적 확약은 소유자 승인 경계를 유지합니다.

## P4 — 기존 Code와 선택적 연결

기존 Code plugin은 이미 존재하므로 다시 만드는 출시 단계가 아닙니다. 별도 bridge에서 저장소·커밋·심벌·정적 근거 참조를 연결합니다. 소스 자동 업로드, Code 분석기의 쓰기 전환, `co:` vocabulary 의미 변경은 금지합니다. 기존 제품 변경이 실제로 필요할 때만 별도 PR과 회귀 시험으로 처리합니다.

## P5 — 입증된 공통 순수 코어 추출

두 실제 소비자가 같은 기능을 사용하는 경우에만 실행 코드를 추출합니다. 인증·DB·LLM·사용자 저장소는 공유 코어로 만들지 않습니다. **네 번째 공개 플러그인을 새로 만드는 것이 아닙니다.** 재사용 이득이 없으면 계약만 공유해도 이 단계의 보류는 합리적입니다.

## P6 — Suite 선택 검토

사용자 수요와 제품별 성과가 확인된 뒤 브랜드 묶음을 검토합니다. 설치·권한·데이터 상속이나 자동 cross-plugin 호출을 가정하지 않습니다.

## 순서 요약

```text
P0 기준선/플랫폼 확인
→ P1a 최소 초안 + 저장/복구 단면
→ P1b 소비자 시험을 통과한 계약 릴리스
→ P2 Contracts 검증 플러그인 / Context 제품 병행
→ P3 각자 공개 등록
→ P4 Code bridge
→ P5 검증된 공통 코어 추출
```

보안·삭제·권한 검증 없이 공개 서버를 노출하지 않습니다. 형식 검증과 제품 시험은 서로 대체하지 않습니다.
