# 08. 시험 및 평가

## 현재 패키지 검증과 제품 검증을 분리

`validate_design.py`는 문서 링크, JSON 파싱, 계약/fixture, 제출 사례 수, 민감 파일 제외, 패키지 무결성 등을 확인합니다. `tests/`는 등록 helper의 fail-closed 동작과 설계 자료의 내부 정합성을 검사합니다. **MCP 제품·보안·성능은 아직 검증하지 않습니다.**

`evals/design-cases.json`은 앞으로 구현할 시험의 명세입니다. JSON에 존재한다는 이유로 실행 통과로 계산하지 않습니다.

## 검증 계층

| 계층 | 검증 대상 | 대표 실패 |
| --- | --- | --- |
| 계약 | schema/형식/필수필드/금지필드 | 모델 생성 approved 필드 수용 |
| 도메인 | 시간·대체·순환·origin 보존 | 미래 결정이 현재 결과에 포함 |
| 영속성 | transaction/revision/idempotency | 재시도로 중복 결정 생성 |
| 격리 | 사용자/프로젝트/검색/근거/내보내기 | 관계 확장에서 다른 사용자 누출 |
| 삭제 | 본문·파생물·캐시·백업 복구 | 삭제 항목이 요약에서 재등장 |
| 검색 | 한국어/영어·동의어·충돌·현재 시점 | 비슷한 다른 프로젝트 결정 반환 |
| 호스트 | OAuth·MCP·승인·Skill routing | 단순 설치를 인증 성공으로 오인 |
| 배포 | lockfile·artifact·rollback·정책 | metadata와 실제 쓰기 동작 불일치 |

## 필수 시나리오

출처 없는 주장, 발명된 source ID, 같은 이름의 다른 프로젝트, 사용자 승인 없는 저장, 승인 후 payload 변경, 만료 승인, 동일 idempotency retry, 동시 대체, supersedes cycle, 미래/만료 시점, 명시적 철회, 실제 삭제, 삭제 후 캐시 hit, 백업 복구 후 부활, 악성 excerpt, 임의 URL SSRF, export 범위, 접근권한 회수, 누락된 tool hint를 포함합니다.

## 평가 데이터

공개 fixture는 모두 가상입니다. 실제 고객사 코드, 사용자 건강/가족/금융 정보, 실제 대화나 비밀을 사용하지 않습니다. 각각의 synthetic record에 기대 source, project, status, validity를 명시합니다.

검색 corpus 제안: 200개 synthetic context, 한국어 60/영어 40 질의, 별도 no-answer/충돌/범위 오염 질의 각 20개. 같은 예제로 모델을 조정하고 평가하지 않도록 dev/test를 분리합니다. 실제 구현 때 규모를 조정할 수 있지만 변경 이유를 기록합니다.

## 제안 gate — 실측치 아님

- 안전 fixture에서 교차 사용자 누출, 미승인 적용, 삭제 내용 재반환: **0건**.
- 현재 사실 필터·대체·동시성·멱등성 계약 시험: 지원한 명세 내 **100% 통과**.
- retrieval Recall@5: 단순 파일/키워드 baseline 이상, 목표 **90%**. corpus별 분모와 실패 예시 공개.
- 답변의 source fidelity: 인용한 근거가 해당 주장을 실제로 뒷받침하는지 수동/독립 평가. 근거 조작 **0건** 목표.
- context pack은 hard character/item budget 준수. 원시 전체 대화 대비 절감률은 동일 작업에서 측정하고 정확도 저하를 함께 보고.
- 기준 환경·데이터량을 명시한 검색 p95 **2초** 목표, 쓰기 승인 이후 처리 p95 **3초** 목표. 승인 대기 시간은 별도 계측.

이 숫자는 성능 약속이나 인증이 아닙니다. 시험 집합에서 0건이라도 모든 공격에 안전하다는 뜻은 아닙니다.

## 플랫폼 검증 matrix

지원하려는 ChatGPT 웹·데스크톱·Codex 표면 각각에 계정 종류, 날짜, plugin 설치 여부, app 연결 여부, tool 발견, 인증, 저장 승인, 조회, 삭제, 재접속 결과를 남깁니다. 하나의 표면에서 성공한 결과를 다른 표면의 지원 증거로 재사용하지 않습니다.

## 공개 제출 자료

공식 포털용 5개 긍정·3개 부정 시나리오의 설계 초안은 `submission/review-cases.draft.json`에 있습니다. 최종 도구 이름·동작을 확정하고 실제 실행 증거를 얻은 다음 제출 JSON으로 변환합니다. 전체 내부 시험은 제출 8개보다 넓어야 합니다.

## v2 평가 확장

`18_EVAL_PROTOCOL.md`와 `evals/v2-design-cases.json`을 함께 적용합니다. 기존 37개 제품 시나리오는 보존합니다. 추가 사례와 실제 작업 benchmark도 실행 전입니다. experiments 시험은 예산 선택의 참조 동작만 검증하고 제품 성능이나 독립 보안 감사를 대체하지 않습니다.
